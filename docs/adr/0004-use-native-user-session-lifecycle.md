# Use native user-session lifecycle managers

Team DevSpace uses each operating system's supported user-session lifecycle manager instead of shipping another supervisor:

- Windows uses Task Scheduler with `InteractiveToken` and `LeastPrivilege`. A small GUI-subsystem launcher creates a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, redirects logs and owns the component process tree without a persistent PowerShell or `cmd.exe` process. Task identity is derived from the persistent local owner, not the remote Device Binding; migration discovers only tasks owned by the same Windows user and exact `TEAM_DEVSPACE_HOME`.
- macOS uses fixed per-user LaunchAgents. The menu-bar app is an `LSUIElement` application and runtime processes remain owned by `launchd`; old device-specific LaunchAgents are retired only when their embedded `TEAM_DEVSPACE_HOME` belongs to the same installation.
- Linux uses fixed systemd user services with native restart policy and journaling-compatible process ownership. Legacy device-specific units are retired only when their embedded `TEAM_DEVSPACE_HOME` belongs to the same installation.

NSIS and macOS Installer remain packaging/bootstrap layers only. They verify immutable offline artifacts and keep replaceable application files separate from Enrollment/project state in the user's private state directory. Windows commits a verified local A/B candidate before first Enrollment so Gateway, DNS or Tunnel failure cannot turn a valid software installation into an installation failure. An already enrolled Windows upgrade reuses the retained Binding/Tunnel credential without contacting the Gateway and restores the prior local startup entries if candidate activation fails. Connection repair is local-first; only missing Enrollment material such as `tunnel.token` may trigger an idempotent re-enrollment with the retained device identity.

We deliberately do not add WinSW, a Windows Service, a privileged daemon, Electron, or another cross-platform supervisor. Those options duplicate native lifecycle management, increase privilege and maintenance surface, and do not fit a product that must run as the logged-in employee with access to that employee's projects and desktop tray. The native mechanisms are documented by Microsoft ([Task Scheduler schema](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)), Apple ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)) and systemd ([systemd.service](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)).

Platform scripts are intentionally thin adapters around those managers. Component scope is preserved during repair: a runtime/tunnel repair cannot retire the tray owner, and an isolated test state cannot retire another installation's startup entries. The native tray also carries its own OS-level single-instance guard (a named mutex on Windows and a per-user advisory file lock on macOS). The controller supplies a SHA-256 identity derived from the canonical private state directory, not the current Access Key or Binding. The same installation cannot create a second icon, while an isolated acceptance home cannot take over or block an employee installation. The native helper rejects a missing or malformed instance identity; launch it through the controller, not directly.

The native UI adapters are intentionally platform-specific: Windows retains Rust/tray-icon/winit; macOS uses a single Swift file with system AppKit/Foundation. Both consume the Node controller's JSON-lines state, and only Node owns business operations and persisted state. macOS key entry and directory selection reuse one short-lived native form instead of AppleScript prompts; no new service, port, persistent store or IPC is introduced. Its separate per-installation form `flock` prevents duplicate dialogs without preventing the tray from staying alive. A cancelled or crashed form cannot abandon an already started binding transaction: the Node caller awaits that transaction before the tray's exit path stops services. Routine progress/success remains in the form/menu; installer recovery alerts remain available when the application cannot start.

Short-lived state-changing operations use one per-state-directory `proper-lockfile` lock shared by CLI commands, tray actions and installer-invoked commands. This reuses an already shipped dependency for atomic acquisition, heartbeats, bounded contention, process-exit cleanup and stale-owner recovery; it is not another supervisor or status store. Nested operations reuse the current operation owner. Read-only status/logs and long-running runtime/tray entrypoints do not take this lock, and key-entry dialogs acquire it only when actually committing a change. A competing mutation either runs after the current operation or reports that it did not execute. It must never overwrite a completed pause with a stale Enrollment snapshot.

Release acceptance is bound to artifacts, not only source tests. Each native package job produces `acceptance.json` containing the release, commit, source-cleanliness state, final entrypoint SHA-256 and the platform checks that actually ran. Publication re-hashes the downloaded entrypoint and refuses evidence from another commit, a dirty CI checkout or different bytes. Windows publication signs first and then exercises that exact signed installer on the isolated runner; local Windows acceptance deliberately uses isolated registry/start-menu identities so it cannot overwrite an employee installation.

Installer progress uses the MUI2 install-files progress handle rather than a dialog control ID, and failure messages distinguish successful restoration from cleanup/restoration failure.
